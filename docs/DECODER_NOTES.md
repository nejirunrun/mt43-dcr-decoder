# デコーダの設計判断・実測で踏んだ落とし穴

切り出し元プロジェクト（自転車用サイクルコンピュータのESP32-S3ファームウェア）の
実装・実機検証で得られた知見のうち、**このデコーダ層 (`dcr_report.h/.cpp`) 自体に
関わるもの**を抜粋する。上位アプリ層（掲示板モデル・地域フィルタ・表示等）の知見は
このリポジトリのスコープ外のため含めていない。

## ① 重複判定に生バイト／CRC24・タイミング情報を使ってはいけない

MT43には確定した区切り・長さ・順番が無く、観測側からその構造を知る術がない。
「同じ情報がカルーセルしているように見える」だけで、ビット列の同一性は保証されない。

1. PAB（プリアンブル）は内容と無関係に巡回し、CRC24の計算範囲bit0〜225の先頭に入る
   → 素のCRC24は同一内容でも変わる。
2. PABを除いてもなお、同一内容の再送が別値になった（実測: 同一通報が3回とも別CRC）。

→ 重複判定・identityは**デコード済みの意味内容**から作る（`dcr_content_key()`）。
生バイトやCRC24は一切混ぜない。

`dcr_content_key()`は「共通部＋詳細デコーダが実装されているカテゴリはその全フィールド」
を材料にする。詳細デコーダの無いカテゴリは共通部だけなので識別粒度が粗い
（同カテゴリ・同時刻の別内容を取り違える理論上の余地が残る）。

## ② EEW（緊急地震速報）と震源を取り違えない

bit121までは同一レイアウトで、そこから分岐する。

| | bit122〜 | 座標 |
|---|---|---|
| 緊急地震速報(category=1) | 予想震度 上下限 → 対象地域80bitビットマップ | **無し** |
| 震源(category=2) | 度分秒の実座標41bit | **有り** |

取り違えると「震度コードを緯度として読む」形で静かに壊れる。必ず`category`で分岐する。

両者はペア配信ではない（気象庁の発表基準が別）:
- EEW … 予測が震度5弱以上 or 長周期地震動階級3以上 → 検知の数秒後、最大優先で連続配信
- 震源 … 観測が震度3以上 かつ 津波の心配なし → 数分後

震度3〜4の地震は**震源だけ**が来る（大多数）。「EEWは座標が無い前提で地域名＋予想震度
だけで完結させる」設計をアプリ側に求める。

さらに震度カテゴリ(3)の観測震度は**3bitの専用表**で、EEWの予想震度4bit表とは値の意味が
全く違う（`dcr_seismic_intensity_name()` と `dcr_intensity_name()` を混同しない）。

## ③ 発令時刻はUTC（JSTではない）

電文の報告時刻・発生時刻フィールドは**UTC**で入っている（実測で確定。受信した全通報が
例外なく日本時間から9時間遅れていた）。表示直前に`dcr_to_jst()`で変換する（生の値自体は
UTCのまま保持——受信直後に足し込むと生データとの突き合わせで混乱するため）。
電文に年が無く閏年を判定できないため、2月28日15:00 UTC以降のみ日付が1日ずれ得る
（既知の限界）。

## ④ 通報区分(Rc)の値割り当て

```
1=最優先  2=優先  3=通常  7=訓練/試験  （0,4,5,6 は仕様上未割当）
```

一次資料 IS-QZSS-DCR-016 の各カテゴリ Parameter Definitions（例 Table 4.1.2-5）に
`Rc: 1: Maximum priority / 7: Training/Test` と明記されている。

切り出し元での実装時、この対応表が丸ごと1つズレて実装され（`0=最大優先 1=優先
2=通常 3=訓練/試験`という誤り）、実災害の「通常」を「訓練/試験」と誤判定する事故に
つながった。**7は優先度の序列の外にある別軸のマーカー**（全ビット1のセンチネル）で、
「通常より下の優先度」として序列に組み込んではいけない。

カテゴリごとに取り得る値が異なる（受信側の検証に使える）:

| Rc | 意味 | 取り得るカテゴリ |
|---|---|---|
| 1 | 最優先 | EEW・津波(警報) |
| 2 | 優先 | 震源・震度・南海トラフ・北西太平洋津波・火山・降灰・気象(発表)・洪水(警報) |
| 3 | 通常 | 津波(解除)・火山・気象(解除)・洪水(解除)・台風・海上 |
| 7 | 訓練/試験 | 全カテゴリ |

## ⑤ ビット幅は必ず一次資料で確認する（洪水予報区40bit事故）

洪水予報区コードは**40bit**（値域 10175000100〜899999999999）。切り出し元では
既存コードのコメント「下位32bitでも衝突は起きない」を鵜呑みにして`uint32_t`へ
切り詰める実装を行い、392件全てで桁あふれが発生する事故を起こした
（10進12桁構造と2進下位32bit抽出という無関係な操作を混同していた）。

このリポジトリの `DcrFlood::region` は `uint64_t`（`dcr_flood_forecast_region_name()`も
`uint64_t`引数）で、この事故を踏まえた型になっている。**新しいフィールドを追加・変更
するときは、必ず一次資料のParameter DefinitionsでExact bit widthを確認してから型を
決めること**（他カテゴリを全数監査した結果、洪水以外は最大でも府県予報区19bit・
海上予報区14bit等で32bitに大きな余裕があり、同型の事故は構造的に起こり得ないことを
確認済み）。

## ⑥ `dcr_content_key()` は全カテゴリの詳細フィールドを混ぜる

このリポジトリの `dcr_content_key()` は14カテゴリすべての詳細デコーダの結果を
指紋計算に混ぜている。切り出し元では当初3/14カテゴリ（EEW・震源・気象）にしか
詳細を混ぜておらず、残りのカテゴリ（台風・海上等）で「報告時刻が同じだけの別内容」が
同一キーに丸め込まれる実害（台風の実況と予報レグの取り違え、SD保全の静かな欠落）が
出た。**新しいカテゴリの詳細デコーダを追加したら、`dcr_content_key()` も同時に
見直すこと。**
